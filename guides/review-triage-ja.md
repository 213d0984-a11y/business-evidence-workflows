# 日本語の宿泊レビューを確認する順番を整理する

宿泊施設のレビューが増えると、担当者が最初に確認する投稿を選ぶだけでも時間がかかります。この手順では、架空のレビュー3件を使い、キーワードと評価から確認順の候補を作ります。投稿の事実確認、緊急時の対応、返信文の判断は人が行ってください。

## 試す前に

[レビュー整理の公開例](https://apify.com/logical_resourcefulnes/hospitality-review-triage-queue/examples/prioritize-hotel-review-responses-demo)を開き、Apifyアカウントにコピーします。実行前にActorの **Pricing** 画面で最新の料金を確認し、実行ごとの最大費用を設定してください。正常に処理したバッチには成果がない場合でも料金が発生する場合があり、開始料金や実行後のデータセット操作料金にも注意してください。

以下は架空のデータです。実際のレビューを使う際は、取得・処理する権限を確認してから入力欄の **I have rights to use this input** をチェックします。氏名、連絡先など、処理に不要な個人情報は入力しないでください。

## 架空データで試す

コピーしたタスクの入力画面で全入力のJSON編集を開き、次を入力します。監視キーは他のデータと共有しない名前にしてください。

```json
{
  "monitorKey": "sample-reviews-jp",
  "rightsConfirmed": true,
  "changesOnly": false,
  "reviews": [
    {"id":"jp-001","property":"架空ホテル","rating":1,"text":"部屋の鍵がかからず、フロントに連絡しました。","date":"2026-10-01"},
    {"id":"jp-002","property":"架空ホテル","rating":2,"text":"夜の騒音がうるさいと感じました。","date":"2026-10-02"},
    {"id":"jp-003","property":"架空ホテル","rating":5,"text":"朝食がおいしかったです。","date":"2026-10-03"}
  ]
}
```

実行後は `review_batch_health` と `review_queue` の行を確認します。上記の架空データをローカルで検証したところ、次の順になりました。この結果は顧客実績でもクラウド実行の記録でもありません。

| ID | 検出されたテーマ | 確認優先度 |
| --- | --- | --- |
| jp-001 | security、service | high |
| jp-002 | noise | normal |
| jp-003 | なし | low |

この判定は、所定の日本語・英語キーワードと評価を使った機械的な整理です。言い回しや文脈によって見落とし・誤検出があります。キーワードの一致は事実の証明ではなく、レビューの原文と状況を人が確認する必要があります。自動で公開返信は行いません。

## 実データへ切り替える

1. 利用権限のあるCSVまたはJSONのレビューを準備し、入力項目と料金をActorのREADMEで確認します。
2. 架空データとの比較を避けるため、新しい監視キーを設定します。同じ一覧の変更を確認する後続実行では、そのキーを再利用します。
3. `changesOnly` を有効にすると、同じキーで再実行した際に変更のないレビューをキューから省けます。全件を見たいときは無効のままにします。
4. メールアドレスや電話番号に似た文字列を出力から隠す機能はありますが、個人情報を完全に匿名化するものではありません。元の入力は実行先のApifyアカウントに保存されます。保存期間と削除方針も確認してください。

[英語版の関連ガイド](operations-triage.md)では、アクセシビリティ所見と営業調査の例も紹介しています。
